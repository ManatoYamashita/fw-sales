# Implementation Plan

> #121 整合・縮小版(D1/D2/D3/D5/D6/D8 を採用、D4/D7 撤去)。移行は expand-contract: Foundation/Core/一部 Integration = PR1(expand)、生成統合・UI 編集・ワークベンチ単線化 = PR2(migrate)、スカラー DROP・構造化資産撤去 = PR3(contract)。

- [ ] 1. Foundation: basic_info 基盤の型とスキーマ (PR1 expand)
- [x] 1.1 基本情報フィールドの型を定義する
  - 1 項目分の値とメタ(取得値・取得区分・確信度・出典・出典抜粋・ヒアリング質問・取得ソース・更新時刻)を表す型と、店舗の基本情報セット全体の型、取得ソース種別(エリア検索 / 手動)を定義する
  - 完了条件: 型が export され `pnpm typecheck` が通過する
  - _Requirements: 2.1_
- [ ] 1.2 51 項目の定義表(キー・ラベル・カテゴリ・既定区分・優先ソース)を整備する
  - 既存 50 項目を母体に、Issue #43 §2 の原典と `schema.ts` を差分照合し、欠落していた 1 項目を特定して追加する。各項目に優先ソース(エリア検索 / 手動)を付与する
  - 完了条件: 51 キーが定義され、全キーに優先ソースが付き、項目総数が定義から動的に算出される
  - _Requirements: 2.1, 2.2, 5.2_
  - _Depends: 1.1_
- [ ] 1.3 店舗テーブルに基本情報カラムを追加する
  - 基本情報セットを格納する jsonb カラムを既定値・空オブジェクトで追加するマイグレーションを作成する。生成 SQL は孤児マイグレ混入を避けるため目視レビューし純粋差分に手修正する
  - 完了条件: マイグレーションが CI で適用され、店舗テーブルに基本情報カラムが存在する
  - _Requirements: 2.1, 8.1_
  - _Depends: 1.1_
- [ ] 1.4 店舗型とリポジトリを基本情報カラムに対応させる
  - 店舗ドメイン型に基本情報セットを追加し、リポジトリの行変換(保存時シリアライズ・取得時パース + スキーマ検証、破損時は空フォールバック)を対応させる。読み取りは基本情報を優先し、未充填項目は既存スカラーで補完する。店舗名のみ必須・基本情報が空でも店舗登録が完了することを保証する
  - 完了条件: 店舗取得で基本情報セットが返り、店舗名のみで新規登録が成功する
  - _Requirements: 1.1, 1.2, 1.3, 2.1, 8.2_
  - _Depends: 1.1, 1.3_

- [ ] 2. Core: 充填・マージ・生成ロジック
- [ ] 2.1 (P) 複数ソースのマージ規則を純関数として実装する
  - 現在の基本情報・1 ソース分の部分更新・取得ソースを受け取り、手動値は自動ソースで上書きしない / 優先ソース一致で上書き / それ以外の自動ソースは未充足時のみ補完、という規則でマージした新しいセットを返す(入力は変更しない)
  - 完了条件: 手動不可侵・優先ソース上書き・空欄補完の 3 規則が入出力で確認できる純関数になる
  - _Requirements: 5.1, 5.2, 5.3, 6.2_
  - _Boundary: mergeBasicInfo_
  - _Depends: 1.2_
- [ ] 2.2 (P) エリア検索結果を基本情報に変換する
  - 地図情報の結果(店名・住所・業態・営業時間・電話・口コミ評価等)を優先ソース=エリア検索の項目キーへ写像し、取得ソースを「エリア検索」として付与した部分基本情報を返す。既存の住所正規化ロジックを流用する
  - 完了条件: 検索結果から取得ソース=エリア検索の部分基本情報が生成される
  - _Requirements: 3.1, 3.2_
  - _Boundary: placeResultToBasicInfo_
  - _Depends: 1.2_
- [ ] 2.3 (P) 生成プロンプト断片と営業資産プロンプト構築を実装する
  - 充足済み項目のみをカテゴリ見出し付きテキストに整形する関数(未充足・未充足のヒアリング項目は省略、推定区分は確信度・出典を併記)と、その断片 + 貼付調査テキスト(構造化しない) + 発信者名から生成プロンプトを組む関数を実装する。フォーム値依存を排し、構造化処理を一切呼ばない
  - 完了条件: 充足項目のみのテキストと貼付テキストが別パートで生成プロンプトに載り、構造化を経由しない
  - _Requirements: 2.3, 4.1, 4.2, 7.1, 7.3_
  - _Boundary: basic-info-prompt_
  - _Depends: 1.1_
- [ ] 2.4 基本情報の原子的マージ永続化をリポジトリに追加する
  - 店舗 ID・部分更新・取得ソースを受け取り、現在値読み取り → マージ純関数適用 → 書き込みを 1 文脈で原子的に行うメソッドを追加する。手動編集値の保存と取得ソース=手動の記録は本永続化層が担う
  - 完了条件: マージ永続化メソッドが原子的に基本情報を更新し、手動値が取得ソース付きで保存される
  - _Requirements: 3.1, 5.1, 6.1_
  - _Depends: 2.1, 1.4_

- [ ] 3. Integration: 充填経路・UI・生成の結線
- [ ] 3.1 エリア検索登録で基本情報を充填する
  - エリア検索からの店舗一括登録時に、取得可能項目をマージ永続化で基本情報へ充填し、取得ソース=エリア検索を記録する。取得できない項目は未充足のまま残す。店舗・一覧キャッシュを再検証する
  - 完了条件: エリア検索登録後、店舗の基本情報が取得ソース=エリア検索で充填されている
  - _Requirements: 3.1, 3.2, 3.3_
  - _Depends: 2.2, 2.4_
- [ ] 3.2 (P) 店舗詳細に基本情報の閲覧表示を実装する
  - 8 カテゴリ 51 項目を見出し付きで表示し、各項目に取得区分(A/B/C)・確信度・出典・取得ソース・未充足を可視化する。移行段階(PR1)では読み取り専用表示に留め、既存スカラーとの二重書き込みを避ける
  - 完了条件: 店舗詳細で 51 項目と各メタ・未充足が読み取り専用で表示される
  - _Requirements: 2.2, 2.3, 2.4, 2.5, 2.6_
  - _Boundary: BasicInfoCard_
  - _Depends: 1.4_
- [ ] 3.3 店舗詳細の基本情報を手動編集可能にする
  - 閲覧表示(3.2)を編集可能にし、手動編集をマージ永続化(取得ソース=手動)で保存する。手動編集値は以後の自動充填で上書きされない。移行段階 PR2 で編集経路を基本情報に一本化する
  - 完了条件: 手動編集が取得ソース=手動で保存され、その後のエリア検索充填で当該項目が保護される
  - _Requirements: 6.1, 6.2_
  - _Depends: 2.4, 3.2_
- [ ] 3.4 既存スカラーから基本情報への backfill スクリプトを実装する
  - 既存店舗のスカラー基本情報(住所・業態・営業時間・口コミ等)を基本情報セットへ変換するスクリプトを作成する。調査結果テーブルは参照しない。dry-run で件数確認 → 適用の 2 段とし、本番直結のため生成内容をレビューする
  - 完了条件: backfill 実行で既存店舗の基本情報がスカラーから初期化され、参照前後で店舗情報の連続性が保たれる
  - _Requirements: 8.1, 8.2, 8.3_
  - _Depends: 1.4, 2.1_
- [ ] 3.5 営業資産生成を単一アクションに統合する (PR2)
  - 充足済み基本情報 + 貼付調査テキスト(任意・構造化しない)を入力に強み・弱み・架電等を生成し店舗に保存・再表示・再生成可能にする統合アクションを実装し、店舗詳細の単一ボタンに集約する。店舗名のみでも実行可能とし、構造化処理を呼ばない。既存の新規登録時 AI 分析と貼付生成の 2 経路を本アクションへ統合する
  - 完了条件: 店舗詳細の生成ボタンで基本情報 + 貼付テキストから営業資産が生成・保存され、構造化処理が呼ばれない
  - _Requirements: 1.1, 4.1, 4.3, 7.1, 7.2, 7.3, 7.4, 7.5_
  - _Depends: 2.3, 1.4_
- [ ] 3.6 調査ワークベンチを単線化する (PR2)
  - 貼付ワークベンチの構造化ステップ・51 項目プレビューの呼び出しを撤去し「貼付 → 生成 → 編集 → 保存」の単線に簡素化する。新規登録時の「AI で分析」導線も撤去する。**呼び出し経路の撤去のみを行い、構造化処理・調査結果テーブルの実体削除は 4.2 が担う**
  - 完了条件: ワークベンチが単線化され、構造化ステップの呼び出しが UI から消える

  - _Depends: 3.5_

- [ ] 4. Contraction: 旧資産の撤去 (PR3, #110 連動)
- [ ] 4.1 調査系スカラー列を DROP する
  - 全消費者が基本情報参照へ切り替わったことを確認後、調査系スカラー列(住所・業態・営業時間・サイト・口コミ等)を DROP するマイグレーションを作成する。本番直結のため backup 前提・生成 SQL レビュー
  - 完了条件: 調査系スカラー列が DROP され、店舗参照が基本情報経由で破綻なく動作する
  - _Requirements: 8.1_
  - _Depends: 3.1, 3.2, 3.3, 3.4, 3.5_
- [ ] 4.2 構造化資産を撤去する
  - 構造化処理・調査結果テーブル・貼付構造化アクション・死蔵 cron の実体を撤去し、項目数表記を実数に整合させ項目総数を定義から動的算出にする。生成経路に構造化が一切残らないことを保証する
  - 完了条件: 構造化処理の実体が除去され、生成が構造化を呼ばず、項目数表記が実数と一致する
  - _Requirements: 7.3, 8.3_
  - _Depends: 3.5, 3.6_
