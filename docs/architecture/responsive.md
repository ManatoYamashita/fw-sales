# レスポンシブ設計アーキテクチャ

`(main)` 配下と `/login` を 375px 幅まで実用的に操作できる状態に保つための規約リファレンス。

- **対象**: 画面幅に応じたレイアウトの出し分け全般（ブレークポイント / コンテナクエリ / 折り返し / 上限幅 / タッチターゲット）。
- **ユースケース**: 営業が外回り先でスマホから店舗を参照・入力する。ゆえに「見えている」だけでは足りず、**到達して操作できる**ことが基準になる。

この文書は Epic #225 の Phase 0 として作られた。個々の機構の契約（閾値表・クラス定数の意味）はソース側の JSDoc が単一の真実で、ここには**横断規約と、過去に踏んだ事故から導いた判断基準**だけを置く（§7 参照）。

---

## 0. 対応範囲

| 幅 | 扱い |
|---|---|
| 375px 以上 | ✅ **全機能が到達・操作可能**であること。横スクロールを発生させない |
| 320〜374px | ❌ 非対応（Epic #225 の非ゴール） |
| タブレット・広帯 | ✅ 対応。ただし「モバイル用の崩しがそのまま出る」状態を許容しない |

`app/layout.tsx` の `viewport` は `width: "device-width"` / `initialScale: 1`。ズームによる回避は前提にしない。

### 検証幅は 10 点

**375 / 414 / 767 / 768 / 1023 / 1024 / 1280 / 1600 / 1999 / 2000px。**

767 と 1023 が入っているのは §2 の非単調点の**片側だけでは回帰を検知できない**ため。1999 と 2000 は `4xl` でメインコンテンツの cap が切り替わる境界の両側。加えて、768px 以上では同一 viewport でもサイドバーの展開・折畳で実効幅が 176px 変わるので、**2 状態とも**確認する。

### 320px を切り捨てた理由

320px は Epic #225 で明示的に非ゴールとした**製品サポート境界**。`/stores` の表は always 列（店舗名 260 + 次回アクション 272 + 操作 100 = 632px）が収まらない帯域でカードへ切り替わり、カードでは同じ情報を縦に積むため、この 632px は 320px 非対応の構造的理由ではない。320〜374px でも偶然操作できる画面はありうるが、全ルートの受け入れ確認と回帰保証は行わない。375px（iPhone SE 相当）を下限に置き、そこを確実に守るほうが実運用と検証コストの釣り合いがよい、という判断である。

## 1. 設計方針

### D1. モバイルファースト

無接頭辞をモバイル基準とし、上へ積む。`max-*:` による打ち消しは、段階表示テーブルなど**意図が明確な箇所に限定**する。

### D2. テーブルはコンテナクエリで列を段階表示する

閾値未満で列を隠す。**always 列の min-content 合計が目標幅に収まらないテーブルに限り、その閾値未満でカードリストへ切り替える**（`/stores` が該当。#234 / PR #236）。切替も同じコンテナクエリ機構で行い、**JS による viewport 判定は使わない**。

JS を使わない理由は 2 つ。PPR の静的シェルは viewport を知らないため hydration 後に DOM が入れ替わってレイアウトシフトとフォーカス喪失が起きること、そしてサイドバー折りたたみに追従できないこと。

### D3. ビューポート依存よりコンテナ依存

要素の折り返し・出し分けの判断は**コンテナ幅**で行う。理由は 2 つあり、どちらも単独で決定的。

1. サイドバーが実行時に折りたためる（240px ⇄ 64px）ので、同じ viewport でもコンテンツ領域は 176px 変動する。
2. 親が grid / flex で viewport ブレークポイントごとに列数を変える場合、**コンテナ幅は viewport に対して単調ですらない**（§2）。

### D4. 固定 px 幅は上限保護を必ず伴わせる

任意値の幅指定（角括弧で px を直書きするもの）や `w-20` のような固定幅は、`max-w-full` か `flex-1` + `min-w-0` を必ず添える。既存の良い実例:

- `store-quick-filters.tsx` — 固定幅に `max-w-full` を併記
- `notification-bell.tsx` — 固定幅に「viewport から左右余白を引いた上限」を `calc()` で併記
- `progress-filter-bar.tsx` — `min()` で viewport 比と絶対値の小さいほうを採る

**flex の子には `min-w-0` を明示する。** 既定の `min-width: auto` のせいで `truncate` が効かず、375px で横溢れする。これは最も踏みやすい事故。

### D5. 回帰検知は in-memory Tailwind compile + render テスト

実ブラウザのスクリーンショット比較は導入しない（CI コストと不安定性）。生成クラスの存在と DOM 構造で担保する（§5）。

### D6. 下限は 375px

§0 のとおり。対応表を更新するときはこの節も直す。

## 2. コンテナ幅の算術モデル

まず、`app/(main)/layout.tsx` 直下のメインコンテンツ幅を次で確定する。

```
メインコンテンツ幅 = min(viewport − sidebar, cap) − padding×2
全幅 Card 直下の DataTable 幅 = メインコンテンツ幅 − Card border 2
```

| 要素 | 値 |
|---|---|
| sidebar | viewport < 768 は **0**（`fixed` のドロワーで場所を取らない） / 768 以上は展開 **240**・折畳 **64** |
| cap | `max-w-screen-2xl` = **1536**。viewport 2000 以上は **2000** |
| padding | `px-4` = 32 / 768 以上は `md:px-6` = **48** |
| Card border | 2（DataTable は Card 直下に置かれる） |

この基礎モデルは #220 / #223 / #224 のブラウザ実測 **11 点で全点一致**している。ただし、Card が grid / flex の内側にある場合は、**メインコンテンツ幅へ親レイアウトの配分を適用してから** Card border を引く。

`/dashboard` の `lg:grid-cols-3 gap-4` 内にある `lg:col-span-2` を例にすると、gap は 16px で 3 列間に 2 本あるため、次になる。

```
2 列 span 幅 = (メインコンテンツ幅 − gap×2) × 2÷3 + gap
DataTable 幅 = 2 列 span 幅 − Card border 2
```

1024px・サイドバー展開ではメインコンテンツ幅が 736px なので、`(736 − 32) × 2÷3 + 16 − 2 = 483.3...px`。§2 の値や PR 本文の実測表をレビューするときは、基礎モデルだけでなく**対象までの親レイアウトをすべて通して**検算する。

### 非単調点 — 「広げたのに狭くなる」

| viewport | 対象 | コンテナ幅 | 何が起きるか |
|---|---|---:|---|
| 767 | 全幅 Card | 733 | サイドバー無し・padding 32 |
| **768** | 全幅 Card | **478** | サイドバーが出現し padding も 48 へ。**−255px** |
| 1023 | `/dashboard` | 733 | grid 1 列 |
| **1024** | `/dashboard` | **483** | grid 3 列の 2/3 幅へ。**−250px** |
| 1999 | 全幅 Card | 1486 | cap 1536 |
| **2000** | 全幅 Card | **1710** | `4xl` で cap が 2000 へ。**+224px** |

**「1024px で N 列」という受け入れ条件は 1023px で成立しない。** 検証幅に境界の両側を入れる理由がこれ。

`--breakpoint-3xl: 1600px` / `--breakpoint-4xl: 2000px` は `app/globals.css` に定義済み。`4xl:` は `app/(main)/layout.tsx` の最大幅 1 箇所で使い、`3xl:` はコード側では未使用。それ以外のブレークポイントは Tailwind 既定。

## 3. テーブルの段階表示とカード切替

契約の実体は `components/ui/data-table-responsive.ts` の JSDoc にある。ここでは**方針として動かしてはいけない点**だけを挙げる。

### 「隠す 1 本」に倒す

「既定で隠し閾値以上で出す」の 2 本立てにしない。Tailwind がクラスを生成し損ねた / コンテナのクラスが付かなかった / ブラウザが container query 非対応、のいずれの経路でも**列が永久に消える**（画面からデータが消える無言の事故）。「閾値未満で隠す」1 本なら、どの失敗経路でも「全列表示＝横スクロールが残るだけ」に劣化する。

カード切替も同じ思想で、表とカードの**両方を DOM に出し、それぞれに「隠す」クラスだけ**を付ける。素の `hidden` を基底クラスに置かない。こうすると失敗時は「両方出る」に劣化し、**「どちらも出ない＝画面が空」は構造的に起こらない**。

### 予算は「そのときのデータでの実測」ではない

閾値は列単体予算の累計で決まる。予算の採り方を 3 回間違えている。

- **cap（`maxWidth`）を持つ列の予算は cap そのもの。** cap は「ここまで伸びうる」という宣言なので、いま入っているデータの実測が下回っても予算は縮まらない（#237 で `/stores` の業態が cap 160 に対し予算 101 になっており、admin に 90px の溢れ帯域を作っていた）。
- **アイコンを持つバッジはアイコンと字間を含めて測る。** 同じ 6 文字でもアイコン無しより 18px 広い（#224 で `/dashboard` の 3 段がまとめて 16px 不足した）。
- **enum 列は全値のうち最長を測る。** `/stores` のチャネルは短い値での実測を採っていた。

閾値は**列幅の丸め和ではなくテーブルの実 min-content** を採る（`/handoffs` は和 717 に対し実測 718 で、717 だとその帯に 1px の横スクロールが残った）。

### 上限の無い列を先に塞ぐ

DB は該当列がすべて `text` で長さ制約が無く、アプリ層の文字数バリデーションも無い。**UI の cap が唯一の予算制御**なので、上限の無い列が 1 つ残るだけで長い値が入った瞬間にその列以降の閾値がまとめてずれる。cap を付けられない列（金額など、途中で切ると誤読させるもの）は**落とす順序の最下位**に置き、後続の閾値を作らないことで無害化する。

## 4. アンチパターン集

### 4.1 実行時に組み立てた Tailwind クラス

Tailwind v4 のクラス生成は**ソースの静的走査**。テンプレートリテラルで組み立てた瞬間に CSS が生成されず、**しかもその失敗は例外を出さない**（単にスタイルが効かないだけ）。閾値クラスは必ず `as const` オブジェクトへリテラルで書き、ソーステキストに逐語で現れることをテストで固定する。

### 4.2 走査対象のファイルに書いたクラス名 (#274)

Tailwind v4 のクラス生成はソースの静的走査で、**走査されたファイルに現れた語は、コードでも散文でも同じように候補になる**。実装が一度も使っていないクラスでも、テストへ渡した引数・JSDoc・ドキュメントの一文に出ただけで本番 CSS に規則が生まれる。

#### 是正前に実際に起きていたこと

`app/globals.css` が `@source` を持たなかったため自動ソース検出が働き、**リポジトリ 743 ファイル**（うちテスト 150 件、Markdown 182 件）が走査対象だった。本番と同じ `@tailwindcss/postcss` で生成した CSS には、実装が使っていない規則が **27 セレクタ**入っていた（base `d0412eb` のクリーンな checkout で実測）。供給元の内訳はこうなる。

| 焼き込まれていたもの | 供給元 |
|---|---|
| 影のユーティリティ（基底の 1 語。カスタムプロパティ群を丸ごと引き込み 2.2KB 相当） | `components/ui/__tests__/class-conflicts.test.ts` の CSS プロパティ対応表 |
| 角丸の辺・隅指定 8 種 | 同上 |
| display 系 3 種と幅の auto、任意プロパティ 1 種 | 同上 |
| flex / align / justify の 4 種（#270 で足した flex の対応表） | 同上 |
| flex の折り返し逆順 1 種 | `__tests__/flex-wrap-right-align.test.ts`（#271） |
| flex の縮小（旧名） | `components/ui/__tests__/modal-classes-css.test.ts` |
| **値が不正な `transition-property` 宣言** | `components/layout/__tests__/sidebar-drawer-css.test.ts` の説明文 |
| リンクの hover 色（基底の 1 語） | `components/ui/__tests__/color-contrast.test.ts`（#273） |
| 色 3 種（emerald の背景・blue の文字・white の文字） | `docs/architecture/color-tokens.md` の散文 |
| 英文の中の "collapse" | `.claude/` 配下のスキル文書 |
| 英文の中の "lowercase" | `.agents/` `.claude/` `.kiro/` 配下の文書 |

つまり **CSS プロパティの対応表を持つガード自身**と、**ごく普通の英文**が、本番 CSS を太らせていた。#265 で `hidden()` を入れたのは同じ機構の 1 例に過ぎず、既知のクラスにしか効いていなかった。

#### なぜ規律ではなく走査範囲で解いたか

"collapse" や "lowercase" は英文散文にごく普通に現れる。これを禁止語として運用すると、**文書で英語を書くたびに Tailwind のユーティリティ名を避ける**ことになり、規律として成立しない。そこで `app/globals.css` で `source(none)` を指定して自動ソース検出を止め、実行時にマークアップを生み得る `app/` `components/` `lib/` だけを `@source` で許可し、その中のテストと Markdown を `@source not` で外した。

実測（本番パイプライン / base `d0412eb` のクリーンな checkout）: 走査 **743 → 304 ファイル**（Markdown 182 → 0 件）、生成 CSS **89,184 → 87,018 バイト（−2,166）**。**消えたのは上表の 27 セレクタと、それらが引き込んでいたテーマ変数 5 個だけで、増えたセレクタ 0・正当な規則の欠落 0。** 設定が効いていること（と絞りすぎていないこと）は `__tests__/tailwind-source-scope.test.ts` が固定する。

#### いま残っている適用範囲

除外が効くのは**ファイル単位**なので、走査対象に残る実装ファイル（`app/` `components/` `lib/` の非テスト）の **JSDoc とコメントに書いたクラス名は、いまも CSS を生む**。実測で 5 セレクタがコメント由来だった。したがって次は今も守る。

- **実装ファイルのコメントに、実装が使っていないクラス名を書かない。**
- **角括弧を含む任意値クラスは、コメントにも文書にも書かない。** 角括弧は中身を伏せても駄目で、形ごと外す。任意値は**単位を検証されない**ので、伏せ字のままでも `width: …` のような不正な宣言がそのまま出力される。説明が要るときは角括弧を使わない散文にするか、数値だけで書く。
- テーマ変数の名前も同じで、**走査対象のファイルに書くと本来 tree-shake される変数が `:root` に残る**。是正前はこの文書が `--breakpoint-3xl` / `--breakpoint-4xl` に言及しているだけで 48 バイトぶん残っていた（`3xl:` はコード側で 1 度も使われていない）。#274 で `docs/` が走査対象から外れた結果、**この 2 つは実際に `:root` から消えた**。実際に使っている `4xl:` の規則は変数ではなく実値へ展開されるため、生成される宣言は是正前後でバイト一致する。色 3 種の変数も同じ経路で消えており、合わせて 5 個。

`docs/` と `.kiro/` と `.claude/` は走査対象から外れたので、そこでの言及はもう CSS を動かさない。それでも**この文書では角括弧つきの任意値を例示に使わない**。除外設定が外れた日に、そのまま再発する形を残さないため。

#### 確かめ方

**「候補集合の差」ではなく「生成 CSS の差」で決める。** 候補集合は篩であって判定ではない。散文に書いた語はクラスでなくても候補として拾われるが、**解決先を持たないトークンは CSS を 1 バイトも生まない**（#262 のガード拡張で §4.3 に例を 1 つ足したとき、候補は 3 つ増えたが生成 CSS はバイト単位で完全一致だった）。

**走査範囲そのものを変えたなら、本番と同じ `@tailwindcss/postcss` を通す。** 候補を手渡す方法では走査を通らないので、`@source` の効果は測れない。ただしこのプラグインは `from` をキーに結果をキャッシュするので、**比較のたびに `from` を変える**こと。同じ `from` で 2 回呼ぶと 2 回目が前回の結果を返し、**「差分 0 バイト」という偽の合格**が出る（#274 で実際に踏んだ）。判定はバイト数だけでなく**セレクタ集合の差**まで見る。

**書いた実測値には、測った base SHA を必ず併記する。** この段落は一度 `c8d2d93` 時点の値（738 ファイル / 18 セレクタ / −1,564 バイト）のまま置かれ、#271 と #273 が入った `d0412eb` の実態とずれた（#275 のレビューで検出）。**base が動いたら測り直す**。数値そのものは typecheck も lint も見ないので、併記した SHA だけが陳腐化を可視化する。測る場所は **クリーンな checkout** にすること — linked worktree では `.git` がディレクトリでなくファイルなので 1 件多く数え、追跡されたシンボリックリンク（`.claude/skills/` から `.agents/` へ）は追従先まで読むため、**走査ファイルの総数は作業環境で数件ぶれる**。ぶれないのは生成 CSS の側で、#274 のバイト差 −2,166 は環境をまたいで一致した。

**走査対象のファイルの中身を変えただけなら**、候補を手渡して測る。手順は次のとおり。**母集合はコード側の候補で、そこへ変更前後の候補をそれぞれ足して比べる。**

1. `app` / `components` / `lib` を Tailwind の Scanner に通してコード側の候補を採る
2. 変更前のファイルと変更後のファイルを別々に Scanner へ通す
3. 「コード ∪ 変更前」と「コード ∪ 変更後」を `components/ui/__tests__/support/build-css.ts` に食わせ、生成 CSS のバイト数を比べる
4. **対照に、リポジトリのどこにも無い実在クラスを 1 つ当て、増えるはずのものが増えることを同時に示す。** 候補集合に無いことを先に `expect` で確かめてから当てる

**対象ファイルだけを候補にして比べてはいけない。** そこに書いたクラスの大半はコードが既に使っているので、単独の差にはコードが生成するぶんが丸ごと乗る。#270 で §4.5 を書き直したとき、文書単独では **+2563 バイト**と出たが、コードを母集合に置くと **0 バイト**だった。**対照も単独では成立しない** — §4.3 が `p-0` に言及しているため `p-0` は既に候補にあり、足しても 1 バイトも増えない（実測）。

**対照に使ったクラス名をこの文書に書かないこと。** 書いた瞬間その語が候補集合へ入り、**次に同じ対照を使おうとした人のところで対照が死ぬ**。#270 で実際に踏んだ（一度書いた名前が、その直後の再計測で「既に候補にある」と弾かれた）。対照は毎回、候補集合に無いことを確かめてから選ぶ。#270 時点の実測は 100 バイト台の増加だった。これをやらないと、壊れたハーネスでも「差分 0 バイト」は出る（§5 の「是正値と誤値の両方で掃引して差分を示す」と同じ理由）。なお `build-css.ts` は `import.meta.dirname` を使うので `tsx` で直接走らせると落ちる。vitest 経由で回すこと。

> **#274 以降、この文書と `docs/` 配下は走査対象ではない。** 上の手順が要るのは走査対象に残るファイル（実装ファイルのコメント）を変えたときで、この文書自体の編集にはもう要らない。それでも手順と対照の作法は有効なので残す。

### 4.3 `cn` に tailwind-merge が無い前提を忘れる

`lib/utils/cn.ts` は素の `clsx`。同じプロパティを持つクラスを 2 つ並べても**打ち消されず両方が出力され、勝敗は「クラス属性の順」ではなく生成された CSS 内の順序**で決まる。

- `size="sm"`（高さ 32px）に `className="h-11"` を重ねる → 記述順勝負
- セル padding を足そうとして既定と重ねる → 記述順勝負

必要なら**variant を追加する**（`button.tsx` の `touch` / `icon-touch` がその例）。既存 variant の値は変えない（波及範囲は `button.tsx` の JSDoc にある。回帰面が読めなくなる）。**正方形のアイコンボタンは `size="icon"` / `icon-sm` / `icon-lg` / `icon-touch` を使う。** `size="sm"` に `h-9 w-9 p-0` を重ねると、`p-0` が `sm` の `px-3` に負けて左右 padding が 12px 残り、中のアイコンが潰れる。

UI プリミティブのサイズ、幅、余白、色を利用側の `className` で上書きしない。`Select` は `width` と `density`、`Spinner` は `size` と `tone`、`Card.Body` は `padding`、`Skeleton` は `tone`、`Button` は `size` / `variant` / `gap` を使い、意図を props で表現する。`Card.Header` / `Card.Footer` は props を持たないので、**行の並べ方 (`flex-wrap` / 寄せ / 交差軸) を利用側から書き換えない** — 変えたいレイアウトは子側で組む (§4.5.1)。`cn` は `tailwind-merge` を持たないため、基底クラスと同じ CSS プロパティを `className` に書くと、どちらが勝つかは生成 CSS の順序次第になる。この 7 つのプリミティブについては `components/ui/__tests__/class-conflicts.test.ts` が `app/` と `components/` の JSX を走査して落とす（ガードは実装の基底クラスを直接読むので、プリミティブ側を変えれば検査範囲も自動で追従する）。`className` は**リテラルでも式でも読む**。式は取り出せた文字列リテラルを合併して検査するので、`className={editing ? undefined : "p-0"}` のように片方の枝だけが衝突する形も落ちる。変数参照のように**クラスを供給しうるのに中身を読めない部分があれば fail-closed で落とす**（#262）。落ちたらクラスを文字列リテラルで書くか、意図を props へ移すこと。新しい例外が必要なら、先にプリミティブへ軸を追加する（`gap-1.5` を通すために `Button` へ `gap` 軸を足したのがその例）。軸を足すときは**基底から同じプロパティのクラスを外す**こと。基底に残すと軸の値と基底が争い、同じ事故が起きる。

### 4.5 `Card.Header` / `Card.Footer` に折り返しが無いまま操作を足す

**#270 で `Card.Header` / `Card.Footer` の双方に `flex-wrap` を入れて解消済み。** 以下は再発させないための背景。

`Card` は `overflow-hidden` を持ち、`Button` の基底は `whitespace-nowrap` を持つ。**縮まないものが、逃げ場のない箱に入っている**構造なので、折り返しが無いと右側の操作は狭幅で切り取られる。`overflow-x: clip`（§6）があるため横スクロールバーすら出ず、症状は「はみ出す」ではなく**「押せない」**として現れる。

**ただし、症状は幅の帯によって 2 段階に分かれる。** #270 の実測（Card 幅 260–900px を 1px 刻み）では、切り取りが起きるのは Card 幅 **294px 以下**（viewport 326px 相当、375px の下限より下）だった。**下限内で起きるのは切り取りではなく「潰し合い」** — `Card.Title` は `h3` で日本語の min-content が文字単位まで小さいため、折り返しが無いとタイトル側が縮んで 2 行になり、ボタンは元の幅を保つ。375px で見出しが 109 → 87px、`WEB資産・連絡先` が 129 → 91px、`action-record` の Footer の 3 リンクが 102 → 91.5px に潰れていた。

**「ボタンが `whitespace-nowrap` だから行が溢れる」と短絡しないこと。** 行の中に縮む余地を持つ子が 1 つでもあれば、溢れずにそちらが潰れる。**どちらが起きるかは足し算では決まらない**ので、§5 の掃引で確かめる。

`flex-wrap: wrap` は各アイテムの**縮小前の寸法**で行を決めるので、`whitespace-nowrap` のボタン群はタイトルと同居できないとき丸ごと 2 行目へ落ちる。タイトルだけが極端に縮む、という中途半端な潰れ方にはならない。

**`justify-content` は行ごとに効く。** 操作群だけが落ちた 2 行目は `justify-between` だけでは左寄せになる。`Card.Header` は**2 番目以降の子へ `margin-left: auto` を与える任意バリアント**を基底に持ってこれを埋める（実物は `components/ui/card.tsx`）。`Card.Footer` は `justify-end` なので不要。

**この規則は消費者へ配らない。** 当初は「操作ラッパへ `ml-auto` を書き、`Card.Header` ブロックを走査するガードで強制する」設計にしたが、`{editing ? 保存群 : 編集}` のように**分岐を持つヘッダでは、ブロック内に 1 つでもあれば通る**ため、negative control（編集モード側だけを外す）が素通りした。**直したはずの回帰そのものを検出できないガード**だった。分岐まで読む走査は壊れやすく、壊れたことも分からない。CSS で構造的に効かせれば検知の問題ごと消える。

「最後の子を右へ」ではなく「2 番目以降」を選んだのは、見出しだけのヘッダで見出しが右へ飛ばないようにするため。子が 3 つ以上のときは auto マージンが余白を等分するので `justify-between` と同じ配置になる。

**`min-w-0` は入れていない。** どちらの子にも `truncate` は無く、`min-w-0` は min-content を割ることを許す指定なので、折り返し先がある構成では要素どうしの重なりを招くだけになる。`truncate` を持つ子を足すときに一緒に入れる。

**overflow メニューへ畳む案は採らなかった。** 編集モードの「キャンセル / 保存」は主操作であり、隠すのは後退になる。操作が副次的で、かつ 3 つ以上並ぶ場合は選択肢に残る（`store-detail-tabs.tsx` の `MoreActionsMenu` が依存ゼロの実装例。ただしパネルを広げるなら位置基準を `components/ui/overlay-anchor-classes.ts` へ寄せること — 狭幅で `absolute right-0` は画面の**左外**へ出る）。

### 4.5.1 プリミティブのクラス列を手書きでコピーする

同じ見た目が要るからといって `flex items-center justify-end gap-2 px-5 py-3 border-t …` のように基底クラス列を写すと、**プリミティブ側の修正が届かない**。#270 の時点で `Card.Footer` のコピーが 2 箇所（フォーム末尾の送信バー）、`Card.Header` 相当のコピーが 2 箇所（`TableSkeleton` / `research-review-section`）あり、いずれも折り返しの修正から取り残される寸前だった。`Card.Footer` は素の `div` なので **`Card` の外でも呼べる**。レイアウトだけ変えたい場合は、プリミティブを呼んだうえで子側で組む（`research-review-section` は `w-full` の子 1 枚に縦積みを閉じ込めている）。

### 4.5.2 `flex-wrap` を `justify-between` の行へ足して、寄せを直さない

**`Card.Header` に限った話ではない。** `justify-content` は行ごとに効くので、`justify-between` の行へ `flex-wrap` を足すと、**操作だけが落ちた 2 行目はその行に要素が 1 つしかない**ため `space-between` が `flex-start` と同義になり、左端へ飛ぶ。1 行に収まっているうちは正しく右端にいるので、広い画面で見ている限り気づけない。

対処は `Card.Header` と同じで、**2 番目以降の子へ `margin-left: auto`** を与える。子が 1 つのときは `* + *` に当たらず、折り返していないときは auto マージンが余白を等分して `justify-between` と同じ配置になるので、**足しても既存の見た目は 1px も変わらない**（下表の「折り返さない幅」の列）。

左端へ飛ぶのは `space-between` だけである。`flex-end` は右、`center` / `space-around` / `space-evenly` は中央になり、どれも事故にならない。

#### 実測（実 CSS を headless Chrome で描画し 1px 刻みに掃引）

| 箇所 | 操作が左端へ落ちる幅 | 帯域数 | 折り返さない幅での是正前後の差 |
|---|---|---|---|
| `handoff-form` の `Card.Body` | Card 幅 260–546px | 287 | 0px |
| `/stores` ヘッダの「店舗を登録」 | viewport 320–488px | 169 | 0px |
| `(legal)` フッタのナビ | viewport 320–553px | 234 | 0px |

いずれも 375 / 390 / 430px を含む。`handoff-form` の閾値 546px は `lg` 2 カラムの 478px より上で、**狭幅だけの問題ではなかった**。媒体クエリを効かせるため、ページ直下の行は iframe を viewport にして測ること（§5）。

#### ガードは成立する（#270 で撤去したものとは検査単位が違う）

`__tests__/flex-wrap-right-align.test.ts` が `app` / `components` / `lib` 配下の TSX を走査し、**同じ要素の class 列**に `flex-wrap` と `justify-between` が揃っていて `[&>*+*]:ml-auto` が無い箇所を落とす。#270 で撤去した走査ガードは「開始タグから閉じタグまでのブロック」を単位にしていたため分岐の片方が欠けても素通りしたが、こちらは**単一の `className` 属性**で完結するので、その失敗モードが存在しない。式で分割して書かれても取り出せるリテラルを合併して拾う（`components/ui/__tests__/support/jsx-class-scan.ts`）。

読めない部分があって判定できない場合は `unprovable` として別に落とす（fail-closed）。ただし対象は「両方が揃っているのに手当てが読めない」場合に限る。`cn(base, className)` で利用側のクラスを受け渡すプリミティブは構造上つねに読めない部分を持つので、「片方だけ + 読めない」まで拾うと `Card.Footer` のような**規則を満たしている側**が毎回引っかかる。その方向のリスク（利用側が `justify-between` や `flex-nowrap` を後から渡す）は `class-conflicts.test.ts` が別途落とす。**2 つのガードは合成して効く。**

### 4.6 `Card` の内側で sticky を使う

`Card` は `overflow-hidden` を持つので内側の sticky は効かない。画面下部固定 UI は Card の外へ出す。また **sticky の位置はスクロールポートの padding box 基準**なので、負マージンで下端に密着させた要素を下端 0 で貼ると非スクロール時に浮く。

## 5. 回帰検知の層

CI は typecheck / lint / vitest の 3 ジョブで、**`next build` を持たない**。つまり CSS 生成は CI では一切ゲートされない。これが下記 ② が存在する理由。

またリポジトリに React component テスト環境が無い。`useState` を動かして「開いた状態」を再現できないため、**マウント後の状態は自動では検知できない**。この制約が ④⑤ の形を決めている。

| 層 | やること | 実例 |
|---|---|---|
| ⓪ 走査範囲検査 | Tailwind が**どのファイルを読むか**を固定する (#274)。②〜⑤ は「読まれた前提」で動くので、読む範囲がずれると全部が的外れになる | `__tests__/tailwind-source-scope.test.ts`。ヘルパは `components/ui/__tests__/support/tailwind-sources.ts` |
| ① ソース逐語検査 | クラスが**リテラル**で書かれているかを `readFile` で直接見る。テンプレートリテラル化という無言の事故を検出する | `data-table-responsive.test.ts` / `modal-classes.test.ts` |
| ② CSS 生成検査 | 本物の `tailwindcss` の `compile()` に本物の `app/globals.css` を食わせ、期待するクエリ・宣言が出ることを確かめる | `data-table-responsive-css.test.ts` / `modal-classes-css.test.ts`。ヘルパは `components/ui/__tests__/support/build-css.ts` |
| ③ 配線検査 | 定数が実際にコンポーネントへ渡っているかを、**開始タグだけを正規表現で切り出して**検査する | `modal-wiring.test.ts` |
| ④ 実描画検査 | 実コンポーネントを `renderToStaticMarkup` し、**実際に出た HTML と class** を見る。①③ と違いソース文字列ではなく結果を見る | `tabs-narrow.test.tsx` / `sidebar-drawer.test.tsx` / `data-table-responsive-cells.test.tsx` |
| ⑤ 純粋関数の単体検査 | 判断ロジックを DOM から切り離した別モジュールへ出し、分岐を網羅する | `tabs-keyboard.test.ts` / `sidebar-focus-trap.test.ts` / `button-touch-target.test.ts` / `jsx-class-scan.test.ts` |

### 土台の完了条件

「回帰検知の土台がある」とは、**層ごとに置き場とヘルパが決まっていて、新しいビューはそれを呼ぶだけで済む**状態を指す。ビューを足すたびに検知方法を設計し直さない、というのが要件である。新しいレスポンシブ対応を入れるときは、次を満たす。

1. **新しいクラスや任意値を導入したら ②。** CI が CSS を見ないので、ここを飛ばすと生成失敗が無言で通る。
2. **レイアウトに効くクラスを持つなら ④。** 「そのクラスが付いていること」はソースではなく描画結果で見る。
3. **キーボード操作・閾値計算・状態遷移を持つなら ⑤。** 判断を純粋関数へ出す。
4. **① は最後の手段。** ソース文字列の検査は、撤去を記録したコメントや説明文へ**自己ヒットして空虚に green** になる。振る舞いとして実行できるなら ④⑤ で実行する。① を選ぶのは「クラスがリテラルであること」自体が争点で、実行しても差が出ない場合に限る。
5. **列挙をテスト側へ写経しない。** 実装が持つ表をそのまま走査する (`BUTTON_SIZE_CLASSES` / 各ビューの `BUDGET`)。写経すると、実装に足した新しい要素が走査対象から漏れて素通りする。
6. **⑤ を成立させるには DOM から切り離す。** Server Action を import するモジュールは、その先の `lib/db` が実 DB 接続を試みてテストが落ちる。純粋部分を別ファイルへ出すこと (`components/layout/sidebar-focus.ts` がその形)。
7. **クラスを供給する場所を増やしたら ⓪。** `app/` `components/` `lib/` の外に実装ディレクトリを足したら `app/globals.css` へ `@source` を書く。書き忘れると**例外は出ず、ただスタイルが効かない**（§4.1 と同じ無言の失敗）。⓪ がそれを落とす。

### この土台で検知できないもの

④ は SSR の初期状態しか描かない。**開閉・フォーカス移動・スクロールロックといったマウント後の状態には自動テストが無い。** ⑤ で判断ロジックの分岐は突けるが、そこから DOM への配線は手動確認に依存する。ドロワー展開時のフォーカストラップ (#253) がこの穴に落ちている。

埋めるには React component テスト環境の導入が要り、それは D5 の「新規依存を避ける」と衝突する。**穴があること自体を書いて残す**のが現時点の扱いで、緑のチェックを「全部検証済み」と読ませないための記述である。

⓪ にも 2 つ穴がある。**(a) 除外はファイル単位なので、走査対象に残る実装ファイルのコメントに書いたクラス名は今も CSS を生む**（実測 5 セレクタ）。これは §4.2 の規律で守るしかない。**(b) ⓪ が「走査対象に入っているか」を検査するのは `*.tsx` だけ**で、`app/` `components/` `lib/` の外に置かれた**クラス文字列だけを持つ `*.ts`** は検知できない。JSX を書けるのは `*.tsx` だけなので実害は出にくいが、クラス定数を新しい場所へ置くときは自分で `@source` を確認すること。

### 空振り検証を必ず添える

②〜⑤ は「常に true を返す形で空虚に green」になりやすい。**存在しないクラスでは生成されない**ことをセットで確かめる。③ で開始タグだけを切り出すのは、検査文字列が**説明コメントに自己ヒット**して空虚に通るのを防ぐため。

### ガードは negative control で検知力を実証してから出す

「テストを足した」だけでは、それが本当に事故を落とすのか分からない。**わざと壊して落ちることを確認し、その結果を PR に残す。** 予算まわりのガードなら「予算だけ動かす」「cap だけ動かす」「ladder から列を落とす」の 3 種で十分に示せる。

**壊し方は「テストが書きやすい形」ではなく「実際に事故った行の原文」を使う。** 同じ欠陥でも書き方が変われば検知できるとは限らない。#262 は、静的なリテラルで作った negative control が全部通っている一方で、同じ欠陥を式で書いた原文は 1 件も落ちない、という形で入り込んだ。

### ブラウザ実測が要るとき

閾値の実測のように「測らないと決まらない」数値は、実アプリを起動せず**実コンポーネントを SSR した HTML を headless Chrome で測る**。手順:

1. HTML は実コンポーネントから作る（`renderToStaticMarkup`）。手で markup を再現すると必ずズレる。enum は全値を別々の行に出せば列幅が自動的に「全値の最大」になる
2. CSS はその HTML の全クラス名を候補にして②のヘルパで生成する
3. フォントは `.next` にある `next/font` の生成物を使い、**必ず HTTP で配信する**。`file://` では `@font-face` が無言で失敗しフォールバックし、数 px ずれて結論が変わる。目的の family 名を明示して `document.fonts.load()` を呼び、戻り値が 1 件以上かつ対象 `FontFace` の `status` がすべて `loaded` であることを結果に含める。`document.fonts.check()` は存在しない family でも true になりうるため、単独の合格条件にしない（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/check)）
4. **校正アンカーを置く。** 検証済みの値を 2 つ以上先に測って完全一致させ、ハーネスの忠実性を立証してから争点の値を測る
5. 掃引はコンテナのラッパ幅を 1px 刻みで動かし、**全幅で**溢れを記録する。遷移点だけ見ると閾値直上の不足を取りこぼす。ウィンドウのリサイズは使わない（コンテナクエリなので不要だし、ブラウザの最小幅にも当たる）
6. **是正値と誤値の両方で掃引して差分を示す**（誤値 → N 帯域 / 是正値 → 0 帯域）。これをやらないと、壊れたハーネスでも「0 帯域」は出る

### 実アプリのルートを測るとき

上は「アプリを起動せずコンポーネント単体を測る」手順。ルート全体の棚卸しのように実アプリを
起動して測る場合は、さらに次を守る。

1. **viewport は iframe の CSS 幅で作る。** ブラウザ拡張のウィンドウリサイズは success を
   返しても実際には広がらない。iframe 内のメディアクエリは iframe の viewport に反応するので、
   基準幅を正確に作れる。**測る前に `documentElement.clientWidth` が指定幅と一致することを
   毎回確かめる** — 一致しない値は捨てる (下記 3 の取りこぼしを検出できる)
2. **iframe の古典スクロールバーを消す。** 実機モバイルはオーバーレイスクロールバーで viewport を
   削らないが、iframe は 8px 削る。補正しないと 375px のつもりで 367px を測ることになる
3. **非同期の掃引ループには世代トークンを持たせる。** ツール側 (CDP) がタイムアウトしても
   **ページ内の実行は止まらない**。前回のループが幅を書き換え続け、`width=414` を指定した
   計測が `clientWidth=2000` を返す、といった偽値が混ざる。実際に 19 世代ぶんが並走していた
4. サーバのストリーミングが止まることがある。React の Suspense 内容が `div[id^="S:"]` の
   隠しコンテナに残ったままなら、それは**計測できない状態**であって「要素が無い」ではない。
   その場合はアプリを介さず、実 CSS を `compile()` で生成した静的 HTML へ切り替える
   (争点が「位置」や「幅」だけなら、アプリの状態は本質ではない)

### 合否は数値で決める

**溢れの判定に目視とスクリーンショットを使わない。** §6 の `overflow-x: clip` と macOS のオーバーレイスクロールバーで見た目は当てにならない。`scrollWidth − clientWidth === 0` を合格条件にする。

**ただし `scrollWidth` は左方向のはみ出しを検出しない。** LTR では左溢れがスクロール領域を作らないため、要素が画面の左外へ出ていても `scrollWidth − clientWidth` は 0 のままになる。`absolute right-0` のようにトリガの右端へ揃える要素は、トリガが左寄りだと**左へ**伸びるので、この指標だけでは素通りする。

実例 (#225 Phase 3、375px viewport): `/stores` の絞り込みポップオーバーは `-216..129` で可視 37%、Topbar の通知ドロップダウンは `-15..305` で可視 95% だったが、**どちらも `scrollWidth` 基準では 0** と出ていた。#261 の棚卸しが両方とも見逃した理由がこれ。

したがって合否は 2 つ揃えて見る。

- `documentElement.scrollWidth − clientWidth === 0` (右方向)
- 各要素の `getBoundingClientRect().left >= 0` (左方向)

## 6. `overflow-x: clip` の扱い

横溢れの抑止は 2 箇所にある。

- `app/globals.css` の `html, body`
- `app/(main)/layout.tsx` のコンテンツラッパ

`clip` を選んでいるのは scroll container を生成せず内側の sticky を壊さないため、という妥当な判断だが、**結果として横溢れが視覚的に「無かったこと」になる**。溢れた要素はスクロールで到達できないので、症状は「はみ出す」ではなく**「操作できない」**として現れる。

したがって:

- 棚卸しや受け入れ確認では **2 箇所とも一時的に外して**測る。片方だけでは隠蔽が残る
- **外せたことを計測前に確かめる。** 両方の要素で `getComputedStyle(el).overflowX` が
  `visible` を返すことを結果に含める。片方だけ外して「溢れ 0」と結論する事故は実際に起きており
  (#261 の棚卸しは `globals.css` 側しか外していなかった)、この確認があれば検出できた
- 「見た目が壊れていない」を根拠にしない（§5 の合否基準）

## 9. 拡張時の指針

1. まず §2 の式でメインコンテンツ幅を出し、対象までの grid / flex 配分を順に適用する。ブラウザを立てる前に机上で決まることは机上で決める
2. 新しい閾値やクラスを足すときは §4.1 / §4.2 を確認する（リテラルで書く・実装ファイルのコメントに使っていないクラス名や任意値を書かない）。**クラスを供給するディレクトリを増やすなら `app/globals.css` の `@source` も足す**
3. 固定幅を置くときは §D4 の上限保護を同時に書く
4. ガードを足したら §5 の negative control で検知力を示し、結果を PR に残す
5. 受け入れ確認は §0 の 10 点（768px 以上はサイドバー 2 状態）。**溢れの判定**は §5 のとおり `scrollWidth − clientWidth === 0` で、これは合否の全部ではない。§0 の「到達して操作できる」を満たすには、加えて **(a) 操作要素のヒットエリア (§8 の 44px 方針)**、**(b) 切り詰めた値へ全文で到達する手段があること (`title` / 詳細への導線)**、**(c) 折り畳んだ操作に可視の手掛かりがあること**を確認する。溢れ 0 はこの 3 つを一切測らない
